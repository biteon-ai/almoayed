# Implementation Plan: BiteonSwitch OTP Auth & Admin Fallback

**Branch**: `005-biteonswitch-otp-auth` | **Date**: 2026-07-21 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/005-biteonswitch-otp-auth/spec.md`

**Feature IDs (registry)**: `AUTH-001` (evolve), `AUTH-002` (evolve), `AUTH-003` (preserve), `AUTH-005` (new)

## Summary

Refactor Al-Moayed authentication so production sign-in is **BiteonSwitch-hosted WhatsApp OTP**, while `/login` becomes **registration-first** (name + WhatsApp + teacher code → create/link profile, no session). Existing users start OTP from a CTA on the same page. After OTP callback verification, mint iron-session with AUTH-003 device lock and role redirects. Add dedicated **`/admin/login`** fallback (WhatsApp + `ADMIN_FALLBACK_SECRET`, allowlisted teacher) for OTP outages. Keep local demo bypass for seeded demo identities.

**Technical approach**: Split today’s combined `loginWithWhatsApp` into `registerStudent` (no session) + BiteonSwitch start/callback + shared `establishSession` helper; add Route Handler callback; thin provider adapter in `src/lib/biteonswitch/`; admin fallback Server Action; optional `/register` rewrite/redirect to `/login`.

**Feature-specific overrides**:

- **Primary Dependencies**: BiteonSwitch hosted OTP (HTTP redirect + server token verify); `crypto.timingSafeEqual` for admin secret compare; no new npm packages expected
- **Storage / tables touched**: `profiles` (read/update `last_session_id`), `student_teachers` (insert on register); new optional `auth_otp_states` (or equivalent) for start/callback `state` + replay protection
- **Performance Goals**: Callback → session → redirect under ~2s server-side (excluding BiteonSwitch UI time); admin fallback under 1 minute end-to-end (SC-004)
- **Constraints**: Constitution passwordless for normal users; secrets server-only; MT-002 unchanged; AUTH-003 on OTP and admin fallback; no admin UI on `/login`
- **Scale/Scope**: Public auth surfaces (`/login`, `/register` alias, `/admin/login`, `/api/auth/biteonswitch/callback`) + auth actions/libs

## Phase 1: Design

See [data-model.md](./data-model.md), [contracts/](./contracts/), [quickstart.md](./quickstart.md).

**Key decisions**:
1. `/login` = registration primary; OTP CTA; `/register` aliases `/login`.
2. `registerStudent` creates profile + `student_teachers` link; does **not** call `establishSession`.
3. BiteonSwitch: redirect to hosted URL → callback Route Handler verifies token → profile lookup → `establishSession` → role home.
4. Admin fallback at `/admin/login`: WhatsApp + `ADMIN_FALLBACK_SECRET`; profile must be `TEACHER` and on `ADMIN_WHATSAPP_ALLOWLIST`.
5. Demo: gated by `AUTH_DEMO_BYPASS=true` (or non-production) for seeded numbers only.
6. Outage UX: Arabic error on OTP start/callback failure; no student emergency path.
7. Replay: one-time `state` row (or consumed jti) before minting session.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| Secret-based admin fallback (exception to constitution “passwordless”) | Guarantees admin access when BiteonSwitch is down (AUTH-005 / SC-004) | OTP-only — fails operational continuity; shared secret alone without WhatsApp — weaker and contradicts clarification Q1 |
| Dedicated `/admin/login` route | Keep fallback off student UI (FR-008) | Toggle on `/login` — exposes/advertises emergency path to students |
