# Implementation Plan: Super Admin Dashboard

**Branch**: `010-super-admin-dashboard` | **Date**: 2026-07-23 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/010-super-admin-dashboard/spec.md`

**Feature ID (registry)**: `ADMIN-001` — platform Super Admin dashboard, teacher CRUD, KPIs, impersonation.

## Summary

Deliver a **Super Admin** area at `src/app/admin/**` for platform governance: KPI overview, searchable teacher roster, create/edit/delete flows (admin-only teacher provisioning), active/inactive toggling, safe quiz disposition on delete, and one-click teacher impersonation with a sticky Arabic return banner. Teachers **never** self-register; public `/login` remains student-only (WhatsApp OTP). Admin-provisioned teachers authenticate via email + password at `/teacher/login`.

**Technical approach**: Migration `006_super_admin.sql` adds `SUPER_ADMIN` role, email/password fields, subject catalog, audit log, quiz archive flag; Route Handlers under `src/app/api/admin/**`; shared guards in `src/lib/admin/`; extend iron-session for impersonation; middleware protects admin routes; UI matches emerald/teal RTL patterns with modals per contracts.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| Constitution #5 — passwordless auth | Super Admin and admin-provisioned teachers require email + password per spec FR-005; students remain WhatsApp OTP | WhatsApp-only for teachers fails spec (email is login username); synthetic WhatsApp is confusing |
| Cross-tenant admin reads | Platform KPIs and teacher roster require global aggregates | Per-teacher session cannot produce platform metrics |
| AUTH-005 route move | `/admin/login` repurposed for Super Admin | Sharing one login URL for emergency teacher + Super Admin conflates roles |
